## 1. 背景：QUndoStack 的六个局限与本框架对策

QUndoStack 是 Qt 官方的撤销框架，心智模型正确（Command 模式 + push 即执行），
但把它放到真实产品里会撞上六堵墙。每一堵墙都有本框架的对应设计：

| # | QUndoStack 局限 | 本框架对策 | 落地位置 |
|---|---|---|---|
| 1 | `beginMacro/endMacro` 手工配对，中途 return/异常泄漏宏（此后所有 push 被吸进永不结算的宏，栈"失灵"且难排查）；无 abort 语义 | RAII `TransactionScope`：析构未 commit → 对已执行子命令**逆序 undo 回滚**后整体丢弃；空事务自动丢弃 | `core/TransactionScope.h` |
| 2 | 合并规则写死：只试"栈顶相邻 + id 相同"，`mergeWith` 语义全塞给命令自己 | 可插拔 `MergePolicy` 栈级策略：相邻同 id / **时间窗**两个内置实现；`mergeTag` 提供极性/换目标阻断 | `core/MergePolicy.h` |
| 3 | 栈不可遍历：只有 `text()/count()`，历史面板、崩溃诊断、脚本都无从下手 | `history()` 返回只读 `Entry` 表（文本/类型/时间戳/字节/context/merged），`setIndex()` 任意跳转且**跨 N 步只发一次信号** | `core/CommandStack.h` |
| 4 | 无 context 概念：多面板/多通道编辑时"我只想撤销属性改动"无解 | Eclipse IUndoContext 式多标签 + `undoIn(ctx)` 向前搜索子序列撤销 | §8 |
| 5 | 命令普遍持目标裸指针：对象删除重建后悬垂（Qt 应用 undo 崩溃的头号来源） | 命令只认 **id + 数据快照**；删除的 undo 按**原 id 重建**，历史里更早的命令重放时仍找得到目标 | §9 |
| 6 | 多信号风暴：`indexChanged/canUndoChanged/undoTextChanged/cleanChanged` 在批量操作时连环触发 | 最小信号面：`indexChanged(int)` 一个信号承载全部刷新，批量操作出口统一发一次 | §5.4 |

另有两处"Qt 没有、别人有"的能力也一并吸收：**字节预算**（Krita/Blender：
大载荷命令只按条数限额不够，§5.3）与**命令序列化**（OCAF/协同系统的
payload 思路，§10）。

## 2. 对标调研：九个项目/体系的 undo 架构对照

> 调研方法：官方文档 + 源码 + 社区一手记录（issue/邮件列表/开发博客）。
> 这张表回答"为什么最终长成第 3 节那个样子"。

| 项目 | 核心机制 | 可借鉴点 | 局限/坑 |
|---|---|---|---|
| **Qt QUndoStack** | Command 模式；push 即执行；id+mergeWith 邻接合并；beginMacro 宏；undoLimit 条数上限；clean 检查点；createUndoAction | 心智模型（push=redo）与 clean/action 集成值得原样保留 | 上表六条 |
| **Eclipse IOperationHistory** | 全局共享历史 + `IUndoContext` 多标签；undo 按 context **过滤子序列并向前搜索**；operation approver 否决机制 | context 过滤是多视图编辑器的刚需，本框架最大差异特性的直接来源 | 完整 invert 语义复杂，本框架取"挖除+重放"简化语义（§8 声明代价） |
| **Krita KUndo2Stack** | QUndoStack 的 fork 改造；**cumulative undo**：时间窗 T1 内、N 步内的相似笔触合并，可发生在历史深处；按颜色/画笔阻断合并；undo docker 显示内存 | 合并策略必须可配置（时间窗+类型白名单）；内存字节感知 | 深处合并语义复杂，"合并了不该合并的笔触"是其反复重写的根因 |
| **FreeCAD** | 事务式："命令即事务记录"——属性变更被 `onChanged` 自动捕获进 `openTransaction/commitTransaction` 区间；属性级 delta；`AutoTransaction` RAII（后补的）；跨文档事务 ID | 自动 delta 捕获省样板；abort 即回滚；RAII 是事后被迫补上的——我们一开始就 RAII | 全属性监听开销大；忘 commit/无配对 abort 的历史 bug（#7580）；空事务"隐身"造成 UI 困惑 |
| **OpenCASCADE OCAF** | `OpenCommand/CommitCommand/AbortCommand`；属性首次修改前 copy-on-write **Backup**，commit 打包 `TDF_Delta`；`GetUndos()` 历史**可遍历**；`SetUndoLimit` 默认 0=关闭 | COW Backup + commit 打包是属性级 delta 最干净的 C++ 范式；历史可遍历 | delta 只覆盖 attribute 世界，视图副作用要自己挂接（历史 bug #0001031）；无合并 |
| **Blender** | 三层体系：全局栈=**整库 memfile 快照**；operator 成功后自动 undo push；编辑模式内局部栈、退出时折叠成一条全局步 | "操作成功后由框架自动 push"的钩子思路；快照式零 per-feature 成本 | 快照内存与文档大小成正比；历史不可编程查询/不可选择性撤销 |
| **GIMP / Inkscape** | GIMP：类型化 undo（~100 种 GimpUndoType）+ 嵌套 undo_group + 内存压力大时老步骤自动升格为快照；Inkscape：对文档 XML repr 树做事务日志（delta） | undo 类型注册表驱动策略（字符串 text 不够表达力）；空组自动丢弃；内存降级思路 | 类型枚举=每加功能交样板税；repr diff 大文档下序列化耗时 |
| **文本编辑器系** | VS Code 启发式分段；Zed 事务+时间窗（#38130 暴露"插入与删除被破坏性合并"）；CodeMirror `newGroupDelay`≈50ms、Quill 1000ms、Syncfusion 300ms；Swing `UndoableEdit.addEdit/replaceEdit` 事件层合并协议 | **时间窗合并是高频输入的业界共识**；合并必须区分语义极性（mergeTag 的由来）；"事件流+合并器"省样板 | 合并粒度是永恒的众怒点（撤太多/撤太少） |
| **协同方向（Figma/CRDT）** | 全局栈语义在多人下崩溃；通行做法=per-user undo + OT/因果调整；CRDT 故意抹掉顺序信息，selective undo 是学术难题 | 命令携带 **actorId + 逻辑时间戳** 作字段级预留，历史模型未来可改造 | 单机 demo 不实现；本框架只在 Command 上留了字段 |

**架构模式对比**（选型依据）：

| 维度 | Command（Qt/本框架） | Memento 快照（Blender） | Delta 记录（FreeCAD/OCAF/Inkscape） |
|---|---|---|---|
| 内存 | 低（参数+小快照） | 高，正比文档大小 | 中，只存被改字段 |
| per-feature 成本 | 每个功能写一对 undo/redo | **近零**（框架一次投入） | 低（属性变更自动捕获） |
| redo 正确性 | **要求命令幂等，最难写对** | 天然正确 | 天然正确 |
| 合并/分组 | 策略自由度最高 | 只能按步折叠 | 事务边界=天然合并边界 |
| 适用 | 操作语义规整的编辑器 | 数据结构异构庞大 | 属性/场景图型文档 |

核心规律：**文档状态越接近"可序列化树/属性表"，越倾向 delta/事务；
状态越异构，越倾向快照；高频小操作（笔触/拖拽/字符）最终都要回到
"命令式 + 强合并策略"**。画布编辑器属于第三类 + 高频手势密集，
所以本框架选 Command 模式为骨、事务为筋、合并策略为魂——
并把 OCAF 式"历史可遍历"、Eclipse 式"context 过滤"嫁接进来。

## 3. 核心设计总览：三条原则与分层

**原则一：栈是历史数据库，不是链表。**
每条命令入账时冻结一份 `Entry` 元数据（文本/类型/时间戳/字节/context/merged），
`history()` 对外只读遍历、`setIndex()` 任意跳转。历史面板、诊断、审计
都从这张表取数——QUndoStack 的"黑盒链表"在这里被换成可查询的账本。

**原则二：命令只认 id，不认指针。**
命令持 `ShapeId + ShapeMeta` 快照；执行前经 `CanvasScene::findShape(id)` 寻址，
找不到按各自规则 no-op。对象删除后 undo 用 `createShapeWithId` **复用原 id**
重建——历史深处引用它的老命令重放时依然命中。悬垂指针在结构上不可能。

**原则三：事务是 RAII，合并是策略。**
多命令原子化不靠手工 `beginMacro/endMacro` 配对，靠 `TransactionScope`
作用域对象（异常安全 + abort 回滚 + 空事务丢弃）；命令合并不靠命令自带的
硬编码规则，靠栈级可插拔 `MergePolicy`（时间窗/相邻 id），命令只提供
判据（`id + mergeTag`）与折叠动作（`mergeWith`）。

**分层**（结构性保证，不是口头约定）：

```
┌────────────────────────────────────────────────────┐
│ app/       MainWindow · InspectorPanel · HistoryDock│  装配层：接线
├────────────────────────────────────────────────────┤
│ commands/  Edit · Geometry · Property · Structure   │  业务命令
│ canvas/    ShapeMeta · ShapeItem · Scene · View     │  画布域(Widgets)
├────────────────────────────────────────────────────┤
│ core/      Command · CommandStack · Compound        │  框架层
│            MergePolicy · TransactionScope           │  ★ 纯 QtCore，
│            CommandFactory · Context · Selection     │    CMake STATIC 库
└────────────────────────────────────────────────────┘    只链 Qt5::Core
```

`undoredo_core` 是 STATIC 库且**只链 Qt5::Core**——框架层若不小心 include
了 Widgets，链接直接失败。分层纪律由构建系统把守（`CMakeLists.txt` §4）。

## 4. Command 协议精讲（`core/Command.h`）

```cpp
class Command {
    virtual void redo() = 0;          // push 时由栈调用（push 即执行）
    virtual void undo() = 0;
    virtual int  id() const = 0;      // 类型 id：合并/策略分派键（业务从 100 起）
    virtual QString text() const = 0; // action 与历史面板文本

    virtual QString mergeTag() const; // 合并许可：空 = 不参与合并
    virtual bool mergeWith(const Command* next);  // 把 next 折进 this
    virtual qint64 estimatedMemory() const;       // 字节预算的输入
    virtual ContextSet contexts() const;          // Eclipse 式标签
    virtual QString payloadType() const;          // 序列化类型名（空=不可序列化）
    virtual QJsonObject toPayload() const;        // 参数包

    SelectionMemento selBefore, selAfter;         // 选择快照（栈自动盖章）
    quint64 actorId; qint64 logicalTick;          // 协同预留字段
};
```

四个协议决策及其理由：

**4.1 push 即执行**（沿袭 Qt）：`stack->push(cmd)` 内部先调 `cmd->redo()`
再入账。命令对象在 push 前不得自行执行——否则效果翻倍。收益：调用点
永远只有一行；redo 路径与首次执行路径是**同一段代码**，不存在
"执行逻辑"与"重做逻辑"漂移的可能。

**4.2 mergeTag 是"合并许可"，默认拒绝**：Qt 的许可是 `id() != -1`，
太粗——同 id 的两条命令可能目标完全不同（改了 A 的颜色又改 B 的颜色，
合并后 undo 一步跨两个对象，用户困惑）。本框架要求 tag **非空且相等**
才许合并，tag 由目标 id 集 + 手势号构成（`commands/CommandIds.h::idsTag`）。
Zed #38130（插入与删除被破坏性合并）的教训制度化：**极性/目标变化必须
阻断合并，而命令 id 表达不了这个维度**。

**4.3 mergeWith 只吸收终态**：约定 `mergeWith(next)` 只把 next 的"to"
折进来，不动自身的"from"。于是合并链的 undo 一步回到**整段连续操作的
起点**（拖拽 3 秒 = 1 条历史 = 1 次 Ctrl+Z 回原点），这是 Krita/文本
编辑器用户已经形成肌肉记忆的行为。

**4.4 幂等纪律（redo 重放安全）**：`undoIn` 的挖除重放、`setIndex` 跳转、
宏重演都会多次调用同一命令的 `redo()`。因此 redo 必须是**"设置绝对终态"**
而不是"施加相对增量"。本 demo 全部命令遵守：
- Move/Resize：`meta.pos = to_`（绝对坐标）
- SetFill/SetStroke：`meta.fill = to_`（绝对值）
- Add：`if (findShape(id_)) return;`（已存在即 no-op）
- Remove：先删后记 `captured_`，重复 redo 时 removeShape 自然 no-op
- 依赖"当时场景状态"的值（`nextTopZ()`）必须在**首次 redo 时冻结**进
  命令（`ReorderZCommand::captured_`），重放时绝不重算。

单测 T1/T11 与电池 S7 专门校验重放等价性。

## 5. CommandStack 精讲（`core/CommandStack.h/.cpp`）

### 5.1 游标模型与 push 九步

栈 = `cmds_`（命令所有权）+ `entries_`（平行元数据表）+ `index_`（游标：
已执行命令数）。`index_` 左侧全部已执行，右侧是 redo 段。

```
push(cmd) 九步（CommandStack.cpp 顶部注释同步）:
① selProvider 盖 selBefore   ② cmd->redo()  ← push 即执行
③ selProvider 盖 selAfter    ④ 宏激活? → 入 macroBuf_ 返回(不发信号)
⑤ 合并判定: redo 段空 && policy->canMerge && top->mergeWith
   → 成功: 更新栈顶 Entry(text/bytes/时间戳/merged), 发一次 indexChanged, 返回
⑥ truncateRedo(): 新命令杀死 redo 段(线性历史语义)
⑦ append + Entry 冻结(text/id/时间戳/字节/context 在此定格)
⑧ trimBudgetQuiet(): 双预算从栈底裁剪
⑨ emit indexChanged(index_) + cleanChanged(仅变位时)
```

⑤ 的两级握手值得强调：**策略说"可合并"之后还要命令自己 `mergeWith`
成功**——策略管"该不该"（类型/时间窗/tag），命令管"能不能"（数据折叠）。
职责分离，两边都可独立替换。

### 5.2 Entry：冻结的元数据

`Entry{text, id, timestampMs, bytes, contexts, merged}` 在 push 时定格，
之后只有合并会更新它（text/bytes/时间戳/merged）。命令对象可能因预算
裁剪被释放，但 demo 里 Entry 与命令同生共死（"命令已裁、元数据留档"
的降级展示被明确砍掉——见 §14 取舍清单）。

### 5.3 双预算截断

`setUndoLimit(steps)` + `setMemoryBudget(bytes)`，任一超限从**栈底**
（最老、离游标最远）弹出，游标与 clean 检查点同步下移。三个语义决策：

- **裁的是历史，不是状态**：被裁命令的效果保留在文档里，只是永远不可
  undo 了（T4 断言 `v == 6` 但 `count == 2`）。
- **单条超预算 → 弹到空栈**：预算是硬承诺，不做"至少留一条"的含糊
  （GIMP 的"老步骤升格为快照"是更优雅的降级，但需要快照基础设施，
  demo 明确不做）。
- **cleanIndex==0 特判**：检查点在栈底又被弹出 → 永久丢失（-1）。
  道理：clean 状态="空文档"，被弹命令的效果已永久烧进状态，那个状态
  再也回不去，不能靠 `index==cleanIndex==0` 假装 clean。与 Qt 行为一致。

字节预算的存在理由（Krita/Blender 实证）：图像/网格类命令单条可达
MB 级，按条数限额会内存爆炸；`estimatedMemory()` 让命令自报载荷，
栈按字节裁剪。

### 5.4 最小信号面

只有两个信号：`indexChanged(int)`（主信号，任何历史/游标变化发**一次**）
与 `cleanChanged(bool)`（仅变位时）。对照 Qt 的四信号
（index/canUndo/canRedo/undoText/redoText/clean…），批量操作时的
信号风暴被消除：`setIndex` 跨 N 步内部逐步执行但**只在出口发一次**，
选择快照也只在终点应用一次（避免中间态闪烁）。T6 用信号计数器锁死
这个契约（跨 3 步 = 恰好 1 次）。

监听方的义务：收到 `indexChanged` 后**整体刷新**自己关心的 UI
（action 文本、历史面板、按钮可用态全部从 `history()/canUndo()` 重取），
不做增量假设。这是"一个信号承载所有刷新"的另一半契约。

### 5.5 setIndex：任意历史点跳转

`setIndex(i)`：i < index 逐步 undo，i > index 逐步 redo，中间步不应用
选择快照、不发信号；终点应用第 i 条的 selAfter（i=0 则清空选择）。
Krita undo docker / VS Code 时间线的核心体验，QUndoStack 也有
（`setIndex`），但配合 `history()` 才真正可用——你知道自己跳到哪。

## 6. TransactionScope 精讲（`core/TransactionScope.h`）

### 6.1 病灶与药方

```cpp
// Qt 式手工配对（FreeCAD 的 openTransaction 同病）：
stack.beginMacro("对齐");
if (!prepare()) { stack.endMacro(); return false; }   // 每条早退分支都要记得配对
for (...) { if (bad) return false; }                  // ← 忘了 endMacro：宏泄漏,
stack.push(...);                                      //   此后所有 push 石沉大海
stack.endMacro();

// RAII：
{
    ur::TransactionScope tx(&stack, "对齐");
    if (!prepare()) return false;        // 析构自动 abort：已 push 的逆序回滚
    for (...) stack.push(...);
    tx.commit();                         // 析构结算：一条 Compound 历史
}
```

FreeCAD 后来补的 `App::AutoTransaction` 就是同一个药方；GIMP 的
`undo_group_start/end` 仍是手工配对（其 issue 列表里配对泄漏有案可查）。

### 6.2 abort 的逆序回滚

析构时未 commit → `rollbackMacroTo(mark_)`：对宏缓冲区里 mark 之后的
子命令**逆序调用 undo()**，然后清空。净效果为零（T10 用抛异常 +
顺序探针验证：回滚顺序严格"后做的先撤"）。异常栈展开自动触发析构，
业务代码里一个 catch 都不用写。

### 6.3 嵌套与结算

- `beginMacro` 记录深度；**最外层文本生效**（嵌套宏折叠进外层，
  与 Qt 一致）；
- 内层 scope 的 mark 是**自己进入时的缓冲水位**，abort 只回滚自己
  之后的部分——内层炸了不连坐外层已成功的部分；
- 结算规则（GIMP `undo_group_end` 同款）：0 条 → 整体丢弃（零栈位
  零信号，"空事务隐身"问题被明确定义）；1 条 → 直入栈（保留子命令
  自己的文本，不套 Compound 壳）；≥2 条 → `CompoundCommand`
  （redo 正序重放 / undo 逆序回滚 / contexts 穿透聚合子命令标签 /
  字节数聚合，id=kCmdCompound 被合并策略恒拒——**宏是原子历史步**）。

### 6.4 事务 vs 单命令原子性：分工

demo 里两种原子化手段并存，分工明确：
- **单命令天然原子**（`RemoveShapesCommand` 一次删 N 个、
  `SetGroupCommand` 一次编组 N 个）→ 不需要事务，一个命令承载整批；
- **多命令协作**（对齐 = N 条独立移动）→ `TransactionScope` 打包。
判断标准：能写成一个内聚命令的就别开事务；事务留给"每条子命令
独立成立、组合起来才是一个用户意图"的场景（`MainWindow::alignLeft`）。

## 7. MergePolicy 精讲（`core/MergePolicy.h/.cpp`）

### 7.1 判定流程

```
push(cmd) → ⑤合并判定:
   redo 段必须为空(index_==count)          ← 与"当前栈顶已执行命令"合并
   && policy->canMerge(top, cmd, tLast, tNow)   ← 策略层：该不该
        AdjacentId: id 相等 && id>=0 && 非 Compound
                    && tag 非空 && tag 相等
        TimeWindow: 上式 && (tNow - tLast) <= windowMs
   && top->mergeWith(cmd)                   ← 命令层：能不能（数据折叠）
   → 更新栈顶 Entry(text/bytes/t/merged) + selAfter, 丢弃 cmd, 发一次 indexChanged
```

与 Krita cumulative undo 的差距是自觉的：Krita 能与**历史深处**的
命令合并（N 步以内），本框架只与栈顶合并。深合并需要"合并可见性
审计"（历史被改写后用户看到的条目会变化），Krita 自己都在这个点上
反复重写过——demo 不趟这潭水，但策略接口（拿到完整判据）已为
扩展留位。

### 7.2 时间窗取值

业界实测数据：CodeMirror `newGroupDelay`≈50ms、Syncfusion 300ms、
Quill 1000ms、Krita 笔触合并 T1 可配。本 demo 取 **500ms**：
拖拽/滑条的事件间隔通常 <50ms（窗口内全折叠），人手"停顿再拖"
通常 >500ms（自然分段）。**一次停顿 = 一条历史**，与用户"我做了
几次操作"的心理计数对齐。

### 7.3 手势号：比时间窗更硬的边界

时间窗是启发式，会误判（拖到一半停顿 600ms → 断成两条）。demo 的
移动/缩放命令把 `gestureId`（每次鼠标按下递增）编进 mergeTag：

```cpp
"move:{排序id集}:{手势号}"     // CanvasView 每次 press ++gestureId_
```

同一次按下-拖拽-松开 = 同一个 tag → 必然合并；松手再拖 = tag 变 →
必然分段。时间窗退化为"手势内部异常停顿"的兜底。**能用确定性边界
（手势/会话）就不要只靠时间启发式**——这是文本编辑器（按词/按句
边界分段）与 Krita（按笔触起止分段）的共同经验。

非手势命令（对齐的子移动，gestureId=0）tag 为空 → 永不合并，
它们的原子性由事务负责（§6.4）。

## 8. Context 过滤精讲（Eclipse IUndoContext 式子序列撤销）

### 8.1 语义

每条命令携带 `ContextSet`（demo 两通道：`canvas` / `inspector`）。
`undoIn(ctx)`：从游标-1 **向前搜索**首条 contexts 与 ctx 相交且
未中和的命令 k，然后：

```
1. 记录当前选择集 selNow
2. cmds_[k]->undo()                    ← 挖除目标
3. neutralized_[k] = 1                 ← 标记中和(不再被搜索/重放命中)
4. for i in (k, index_): 未中和则 cmds_[i]->redo()   ← 升序重放
5. 恢复 selNow；游标不动；发一次 indexChanged
```

净效果 = 精准挖掉 k，其余通道的状态**不变**（重放不变式，T13/S6 断言）。
demo 的「只撤销一步属性改动」按钮就是 `undoIn({"inspector"})`：
画布上图形的位置纹丝不动，颜色回退一格。

### 8.2 代价声明（如实）

这是**演示语义**，不是 Eclipse 的完整 invert 语义。三条边界：

1. **依赖幂等**（§4.4）：重放 = 再次 redo，相对增量式命令会被放大；
2. **中和标记是单向的**：被挖除的命令仍在历史里（线性 undo/redo/
   setIndex 会正常重放它），但不再参与子序列搜索。"挖除后再线性
   undo 穿越它"会把它当作普通命令撤销——两种视角叠加时的语义
   没有完美方案（这正是 CRDT selective undo 至今是学术难题的原因，
   §2 协同行）；
3. **依赖链降级**：若 k 之后的命令依赖 k（改了颜色→删了对象），
   挖除 k 时对象已删 → 按目标安全规则 no-op，不崩不误建（S9 专测）。

### 8.3 Compound 的穿透

`CompoundCommand::contexts()` 返回子命令标签的**并集**——事务里
混有属性改动时，`undoIn({"inspector"})` 能命中整个事务（粒度是
整条 Compound，不拆内层）。这是刻意保守：拆开重放半条事务会破坏
§6 的原子承诺。

## 9. 目标安全与选择快照

### 9.1 为什么命令不持指针

画布对象会被删除、被 undo 重建。若命令持 `ShapeItem*`：
删除后重建的新对象是**新地址**，历史里引用旧地址的命令全部悬垂
（Qt 论坛 undo 崩溃帖的头号根因）。本框架的解法是一条身份链：

```
ShapeId(quint64) = 身份          ShapeItem* = 当下住处(可随时失效)
命令存: id + ShapeMeta 快照      执行时: scene->findShape(id) 现场寻址
删除的 undo: createShapeWithId(原 id, 快照) → 身份复活, 老命令重新可达
找不到目标: 各命令按幂等规则 no-op(不崩、不误建、不半执行)
```

`CanvasScene` 是唯一收口点（`canvas/CanvasScene.h` 头注释）：
对象生命周期（create/createWithId/remove）与状态读写（getMeta/setShapeMeta）
全部经过它——**没有旁路 = 没有不可撤销的操作 = 没有失联的对象**。

### 9.2 选择快照的时机矩阵

选择集不单独入栈（每次点选吃一条 undo 是历史污染），而是作为命令
附带状态。栈配置 `SelectionProvider/Applier` 后全自动：

| 时机 | 动作 |
|---|---|
| push 前 | provider 盖章 `selBefore` |
| cmd->redo() 后 | provider 盖章 `selAfter`（命令 redo 里的 setSelection 被自然捕获） |
| undo 步 | applier 恢复 `selBefore` |
| redo 步 | applier 恢复 `selAfter` |
| setIndex 批量 | 只在**终点**应用一次（中间态不闪烁） |
| undoIn | 记录并恢复"当下选择"（游标未动，选择不该动） |
| 宏 | Compound 继承首子的 selBefore / 末子的 selAfter |

S3 实测：删除选中的图形 → undo → 图形按原 id 回来**且仍处于选中态**。

## 10. 序列化就绪：payload 与工厂

**命令 = 类型名 + JSON 参数包。** `Command::payloadType()/toPayload()`
+ `CommandFactory::registerType/fromPayload` 构成通路：

```cpp
// main/SelfTest 装配时注册（creator 绑定场景指针）：
CommandFactory::instance().registerType("cd.addshape",
    [scene](const QJsonObject& d){ return AddShapeCommand::fromPayload(scene, d); });
// 执行时留档 → 任意时刻重建回放：
QJsonObject doc = CommandFactory::toPayloadDoc(cmd);      // {"type","data"}
auto rebuilt = CommandFactory::instance().fromPayload(doc);
stack->push(std::move(rebuilt));                          // S10: 回放等价
```

诚实声明两处取舍：
- demo 只给 `AddShapeCommand` 做了**可回放**的完整往返（"绝对终态"式
  命令最适合序列化：payload 只需 {meta, id}）；`SetFillCommand` 只有
  `toPayload`（**审计日志形态，单向**）——from 状态依赖执行时机，
  重建后 undo 语义不完整，与其做一个半吊子回放不如如实标注；
- 全栈持久化（保存/打开 undo 历史）明确砍掉：`history()` 的 Entry 表
  + payload 已经把地基打好，产品化时按 §14 的清单补即可。

协同预留：`Command::actorId/logicalTick` 两个字段（无逻辑）。真做
per-user undo 时，历史模型不需要重构——这是 §2 协同调研留下的钩子。

  `index()==idx+1 && count()==index()` 断言（redo 段被截断本身就是
  被测行为）。教训：**count 混着 redo 段，index 才是"已发生的历史"**。

## 13. 踩坑记录（本工程实测，全部有修复提交在案）

1. **`QVector<quint64>({3})` 单元素花括号列表被 MSVC 绑到 `QVector(int size)`**
   ——构造出 `{0,0,0}` 而不是 `{3ull}`！两元素 `{1,2}` 反而正常走
   initializer_list。诊断现场：比较双方逐元素打印才现形（expect: size=3
   id=0 id=0 id=0）。修复：整型字面量**必须带 ull 后缀**，让 int 构造
   因窄化转换出局。教训：单元素 brace-init 撞上"接受整型的显式构造"
   是静默错值，不报错不崩溃，只有断言失败——排查时先打印**期望值
   本身**，别只打印被测值。
2. **测试断言基准选错（S4）**：redo 段的存在让 `count` 不是"历史长度"
   的可靠代理，见 §12。
3. **`qputenv` 是小写 p**：`qPutEnv` 不存在（C3861），Qt 的 env 三件套
   是 `qgetenv/qputenv/qunsetenv`。
4. **QWidget 面板进 dock 必须包 `QDockWidget`**：`addDockWidget` 只收
   `QDockWidget*`，直接传自定义 QWidget 编译期就拦（C2664）——这是
   好事，Qt 的类型系统在这里替你把关。
5. **"只排 meta 不排 (id,meta) 对"会丢 id**：`distributeH` 初版把
   `QList<ShapeMeta>` 排序后找不到对应 id，写了个 break 占位差点
   蒙混过关。修复：排序单位永远是 `QPair<ShapeId, ShapeMeta>`。
   教训：**并行数组是 bug 温床，成对数据用 pair/struct 绑死**。
6. **既有坑位复认**（知识库已录，本工程再次验证有效）：/utf-8 必加；
   printf 格式串只用 ASCII 装饰符（`→★` 会触发 C4474 破坏参数检查）；
   含 Q_OBJECT 的头必须显式列进 target 源列表（STATIC 库同理，
   `undoredo_core` 的 CMake 注释里写死了这条）；MSVC 多配置产物在
   `build/bin/Debug|Release` **双层路径**（launch.json 别照抄单层工程）。
