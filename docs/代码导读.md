# 代码导读 —— 从零读到能改

这份文档只回答一件事：**按什么顺序读、每一站盯住什么**。
机制为什么这么设计，见 [设计精讲.md](设计精讲.md)；这里不重复推导。

---

## 0. 五分钟速览

一句话：**一个零 Qt 的命令栈内核，配一层 Qt 画布外壳**。

```
        ┌─────────────────────── demo 层（Qt5 Widgets） ───────────────────────┐
        │  CanvasView ──手势──▶ 业务命令 ──push──▶ ┌──────────────┐            │
        │  (鼠标→命令)          (commands/)        │ CommandStack │◀── core    │
        │                                          │  cmds_ +     │   零 Qt    │
        │  HistoryDock ◀─Qt信号── StackBridge ◀────│  entries_ +  │            │
        │  InspectorPanel        (Observer→信号)   │  index_      │            │
        └──────────────────────────────────────────┴──────────────┘────────────┘
                     ▲ 所有状态读写都经 CanvasScene（唯一收口点）
```

三条铁律，先记住再读代码：

1. **push 即执行**：命令的 `redo()` 就是"做这件事"本身，不存在"先改界面、
   事后补一条命令"的旁路。所以实时拖拽 = 每个 mouseMove 都 push 一条
   （靠合并策略折叠）。
2. **命令不持对象指针**：只存 `ShapeId + 数据快照`，执行时 `scene->findShape(id)`
   现场寻址。删除后 undo 按**原 id 重建**。
3. **一个通知刷新一切**：`CommandStack::Observer::onIndexChanged` 是唯一出口，
   监听方收到就整体重取 `history()/canUndo()`，不做增量假设。

三层职责一句话版：

| 层 | 目录 | 只干这件事 | 依赖 |
|---|---|---|---|
| core | `src/core/` | 撤销/重做语义、合并、事务、context、序列化工厂 | 纯 C++17，**零 Qt** |
| domain | `src/canvas/` + `src/commands/` | 画布数据模型 + 业务命令 | Qt Widgets |
| app | `src/app/` | 装配、手势翻译、面板、自测 | 上面两层 |

> core 的"零 Qt"不是口号：`-DUR_BUILD_DEMO=OFF` 时整个 demo 都不编译，
> 单测照样跑（139 断言）。所以 core 里看到 `#include <Q...>` 就是 bug。

## 1. 推荐阅读路线（约 2.5 小时，可按需跳）

时间预算按"读得细"估的；只求能改代码可以只走 ①→③→⑥。

### ① 先跑起来，让测试输出当地图（10 分钟）

```bat
D:\CMAKE\bin\cmake.exe -S . -B build -G "Visual Studio 16 2019" -A x64
D:\CMAKE\bin\cmake.exe --build build --config Debug
build\bin\Debug\unit_tests.exe                     :: 139 断言，退出码 = 失败数
set PATH=D:\Qt\5.15.2\msvc2019_64\bin;%PATH%
build\bin\Debug\undoredo_demo.exe --selftest       :: 44 断言，offscreen
build\bin\Debug\undoredo_demo.exe                  :: 手动玩一遍
```

**手动要试的四件事**（它们分别对应四个核心机制，玩过再读代码会有画面）：
拖一个图形（看历史面板出现 `<merged>`）、拖滑条（看它被折叠成一条）、
点历史面板中间某行（跳转）、按「只撤销属性改动」（画布不动、颜色回退）。

### ② 协议：`src/core/Command.h`（15 分钟）

只有 7 个虚函数，但每个都有"为什么"：

| 成员 | 什么时候被调 | 读的时候盯住 |
|---|---|---|
| `redo()/undo()` | push / 撤销 / 重放 | 注释里的**幂等纪律**：redo 设绝对终态，undo 是它的逆 |
| `id()` | 合并判定、历史面板着色 | 负数 = 无效；`kCmdCompound` 永不合并 |
| `text()` | 历史面板、按钮文案 | 必须是"用户语言"，不是类名 |
| `mergeTag()` | 合并判定 | **空 tag = 拒绝合并**（极性键） |
| `mergeTagHasSession()` | 时间窗策略 | 返回 true = tag 里含手势/笔画号，时间窗让位（§7.3） |
| `mergeWith()` | 合并成功时 | 只吸收**终态**，不累加增量（否则重放放大） |
| `estimatedMemory()` | 字节预算 | 默认 `sizeof(Command)` 只是兜底，派生类必须自报载荷 |
| `contexts()` | `undoIn` 搜索 | demo 两通道：`canvas` / `inspector` |

读完自测：为什么 `mergeWith` 不能简单地把两条命令的"增量"相加？
（答案在 §4.4 / T11：重放 = 再 redo 一次，相对增量会被放大。）

### ③ 内核：`src/core/CommandStack.h` 的头注释 → `.cpp` 的 `push()`（30 分钟）

`CommandStack.h` 顶部的注释就是全文摘要，先读它。然后按这个顺序读 `.cpp`：

```
push()                ← 九步流水线（合并 → 截断 redo → 入账 → 裁剪 → 通知）
appendExecuted()      ← push 与"宏结算"共用的入账后半段
trimBudgetQuiet()     ← 双预算，一次 erase 区间（O(n)，不是循环 erase）
undo()/redo()         ← stepUndoInternal/stepRedoInternal（各自一步，游标±1）
undoIn()              ← 子序列撤销：移除一条 + 升序重放 + 截断 redo 段
setIndex()            ← 跨 N 步只发一次通知、只在终点应用选择
endMacro()            ← 0 条丢弃 / 1 条直入 / ≥2 条包 Compound
emitCleanIfChanged()  ← clean 只在变位时通知
```

**这一站的核心是"历史里没有洞"**：`cmds_` 的每个下标都对应一个真实状态，
`index_` 左侧全已执行、右侧全是 redo 段。`undoIn` 不是"标记某条失效"，
而是**真的把它从历史里删掉**（游标左移、redo 段作废）。

```
初始:        [A B C D | ]            index_=4
undoIn(命中B): [A C D | ]            index_=3  ← 撤销 B、重放 C/D、删 B
之后 setIndex(0..3) 的每个停点都精确等于"前 j 条重放"
```

为什么不做"挖洞+位图"（早期方案）：面板高亮就是 `index_`，洞会让
"点哪行"和"看到什么"脱钩，且 redo 段里同通道命令的基线快照会失真。
完整推演与实测反例见 `设计精讲.md` §8.1.1。

### ④ 合并：`src/core/MergePolicy.cpp` + `src/commands/GeometryCommands.cpp`（20 分钟）

两级握手，职责分离：

```
策略（MergePolicy）回答"该不该合并"：同类 id + tag 非空且相等 + 时间窗/会话
命令（mergeWith）  回答"能不能合并"：数据能不能折叠成一个终态
```

重点看 `TimeWindowMergePolicy::canMerge` 的三段：`mergeCompatible` →
`mergeTagHasSession()` 直接放行 → 时间窗比较。再看
`MoveShapesCommand::mergeWith` 怎么用 `from_/to_` 覆盖而不是累加，
以及 `mergeTag()` 里 `idsTag(...)`（定义在 `CommandIds.h`）+ `gestureId_` 的拼法（手势号是硬边界）。

### ⑤ 事务与宏：`TransactionScope.h` + `CompoundCommand.cpp`（15 分钟）

`TransactionScope` 是 60 行的 RAII 类，读三个点：构造函数 `beginMacro`、
`commit()`、析构里的 `rollbackMacroTo(mark_)`（异常/早退自动逆序回滚）。
`CompoundCommand` 只做四件事：转发 redo/undo、contexts 取并集、选择快照取
首尾、`estimatedMemory` 求和。

### ⑥ 画布域：`ShapeMeta.h` → `CanvasScene.h/.cpp` → `CanvasView.cpp`（30 分钟）

- `ShapeMeta.h`：纯数据快照 + `operator==`（浮点比较走 `cd::fuzzyEqual`）。
  合并键里的目标集合串 `idsTag(...)` 在 `commands/CommandIds.h`（排序后拼接，
  保证同一集合只有一种写法）。
- `CanvasScene`：**唯一收口点**。读 `createShape/createShapeWithId/removeShape/
  getMeta/setShapeMeta/selectIds`。`selectIds` 是差量实现（同集合零副作用），
  因为 QGraphicsScene 的 `clearSelection()+setSelected()` 会发一堆
  `selectionChanged`（S11 就是为它写的回归）。
- `CanvasView.cpp`：手势 → 命令的翻译层。`mousePressEvent` 里
  `++gestureId_`、`beginResizeIfHandleHit` 的命中判定、
  `pushMoveStep/pushResizeStep` 每个 move 都 push。注意它**没有** keyPressEvent
  ——Delete 由工具栏 QAction 的快捷键统一处理（一个删除入口）。

### ⑦ 装配与生命周期：`StackBridge.h` → `MainWindow.h/.cpp`（30 分钟）

`StackBridge.h` 里有两个东西：

```cpp
class StackBridge : public QObject, public CommandStack::Observer { ... };
struct StackHost { CommandStack stack; StackBridge bridge{&stack}; };
```

`StackHost` 把"bridge 必须先于 stack 死"焊进类型里（成员逆序析构），
`MainWindow` 只持有一个 `ur::StackHost stackHost_`，不再手写 unique_ptr 顺序。

然后读 `MainWindow.cpp` 的**三段**，顺序很重要：

1. 构造函数 → `buildUi()`（控件树）→ `wireStack()`（信号接线）→ `onCleanChanged(true)`；
2. 各个 `addShape/deleteSelected/alignLeft/...` 槽：它们是"用户意图 → 命令"的
   唯一入口，`alignLeft` 是 `TransactionScope` 的样板；
3. **`~MainWindow()`**：显式按依赖序拆 UI（view → 两个面板 dock → scene）。
   为什么不能交给 `~QObject`？因为 scene 析构会清选择集并**发信号**，
   而监听它的 `InspectorPanel` 那时可能还活着 → 回调半销毁对象（§13.9，
   这是本工程唯一一个"真实用户关窗就会踩到"的崩溃）。

### ⑧ UI 消费端：`HistoryDock.cpp` + `InspectorPanel.cpp`（20 分钟）

`HistoryDock::refresh()` 是"最小通知面"的教科书用法：条目数变了才
`rebuildRows()`，否则只 `updateRows()`（靠 `shown_` 文本缓存跳过没变的行），
再 `highlightCursor()` + `updateStats()`。注意 `refreshing_` 这个重入闸
（`setCurrentRow` 会触发 `currentRowChanged` → 又回调 `setIndex`）。

`InspectorPanel` 的重点不是 UI，而是它**每个滑条刻度都 push**：
`valueChanged` → `SetFillCommand`，500ms 时间窗折叠。滑条拖到一半松手、
再拖，就会分成两条历史——这就是 §7.2 的"一次停顿 = 一条历史"。

### ⑨ 测试怎么读：`tests/unit_tests.cpp` → `src/app/SelfTest.cpp`（25 分钟）

单测按 T1~T20 顺序读，**先读每个块开头的注释**（写了"这块锁的是什么契约"），
再看断言。两个测试替身值得单独看：

- `TestCommand`：相对增量式（`mergeWith` 累加 `bytes_`），专门用来暴露
  "重放放大"和"重复撤销"；
- `UndoCounter`：数 `undo()` 被调了几次，T16 用它锁死"移除一步只撤一次"。

`SelfTest.cpp` 的 S1~S12 是"真实 MainWindow + 真实命令"的集成电池。读 S11
（`selSignals` 探针）能一次看懂差量选择；读末尾的 `w.reset()` + 打印
"teardown: MainWindow 析构完成"能看懂退出路径的回归门。

## 2. 一次拖拽的完整时序（把上面的站点串起来）

```
mousePressEvent                    CanvasView.cpp
  ++gestureId_                     ← 硬边界（会话号）
  记录 pressScenePos、选中集
mouseMoveEvent (每个事件)
  pushMoveStep()
    构造 MoveShapesCommand(from_, to_, ids, gestureId_)
    stack->push(cmd)
      push() ① selBefore ② cmd->redo()（= 真的移动图形）③ selAfter
             ④ 宏？否  ⑤ 合并判定：
                 AdjacentId: id 相同、tag 相同（同 ids + 同 gestureId）
                 TimeWindow: mergeTagHasSession()==true → 直接放行
                 top->mergeWith(cmd)：from_ 保留、to_ 覆盖
                → 更新栈顶 Entry(bytes/text/merged=true) → trimBudgetQuiet
                → onIndexChanged 一次
              （合并失败才会走到 ⑥ 截断 redo ⑦ 入账 ⑧ 裁剪 ⑨ 通知）
  StackBridge::onIndexChanged → emit indexChanged
    MainWindow::onIndexChanged → 刷新 action 文案/标题 * 号
    HistoryDock::refresh → 条目数没变 → 只改栈顶那行文本 + 高亮游标
mouseReleaseEvent
  清临时状态（gestureId_ 保留到下次 press 再 ++）
```

一次拖拽 = **一条历史**，即使中间产生了 300 个命令。

## 3. 概念对照表

| 词 | 在哪 | 一句话 | 容易误解的点 |
|---|---|---|---|
| `Entry` | `CommandStack.h` | push 时冻结的元数据（text/id/时间/bytes/contexts/merged） | 合并会更新它；命令被裁剪时 Entry 一起走（demo 不做"留档"） |
| `index_` | `CommandStack.h` | 已执行命令数（游标） | **不是** `count()`：右侧可能有 redo 段 |
| `contexts` | `Command.h` / `Context.h` | 命令属于哪个通道（canvas/inspector） | `undoIn` 是"移除一步+重放"，不是"过滤视图" |
| `cleanIndex_` | `CommandStack.h` | 保存检查点位置，-1 = 无/已丢失 | 检查点被预算裁掉 → 永久 -1（不能假装 clean） |
| `mergeTag` | 命令 | 合并许可键；空 = 拒绝 | 同 id 但 tag 不同 → 不合并（换目标就断开） |
| `mergeTagHasSession` | 命令 | tag 里含手势/笔画号 | 为 true 时时间窗**完全不参与** |
| `macroBuf_` | `CommandStack.h` | 宏期间的子命令暂存区 | 宏激活时 push 不通知、不截断 redo |
| `StackHost` | `StackBridge.h` | stack + bridge 的绑定体 | 析构顺序由成员序保证，别拆成两个成员 |

## 4. 常见困惑 Q&A

**Q：为什么 `push()` 里先 `redo()` 再入账？先入账不行吗？**
A：因为"执行"可能失败/降级（目标已删 → no-op）。先执行才能让选择快照
`selAfter` 捕获到命令真实造成的选择变化；而入账只关心"已执行的命令"。

**Q：为什么命令不直接改 `ShapeItem`，非要绕 `CanvasScene`？**
A：绕过去就绕过了 undo。`CanvasScene` 是唯一收口点，命令只能通过它读写，
于是"没有不可撤销的操作"。这也是为什么 `ShapeItem` 故意不设 `ItemIsMovable`。

**Q：`setIndex()` 和连续调 `undo()` 有什么区别？**
A：前者中间步不应用选择快照、不发通知，只在终点发一次；后者每步都发。
批量跳转必须用 `setIndex`，否则历史面板会闪 N 次。

**Q：`undoIn` 之后游标为什么左移了？**
A：它把命中的那一步**从历史里删掉**（不是打个洞标记失效），所以游标随
历史长度一起减一、面板高亮跟着走。这样"点哪一行就精确回到哪一行"才成立。
代价：那一步不能再重做，原有 redo 分支也一并作废（与 push 同规则）。

**Q：为什么 `HistoryDock` 要自己缓存文本，不直接 `setText` 全量刷？**
A：`QListWidget::item(i)->setText()` 会触发重绘/布局；滑条拖动时每秒几十次
通知，全量刷会掉帧。缓存 `shown_` 后只有真正变化的行才 setText。

**Q：`StackBridge` 为什么不能 `new StackBridge(&stack, this)`（挂 parent）？**
A：QObject parent 会把析构推迟到 `~QObject` 阶段，那时 `stack` 成员已经死了，
`~StackBridge` 里的 `removeObserver` 就是 UAF。用 `StackHost` 的成员序即可。

**Q：`registerType` 的 creator 为什么要收 `CommandContext&`？**
A：不收就得靠 lambda 捕获场景指针，把全局注册表和瞬时对象焊死（悬垂）。
显式注入后注册与实例解耦：可以在场景创建前注册，回放时把上下文传进来，
类型不对就返回 nullptr 走降级路。

## 6. 动手改：两个最常见的任务

### 加一条新命令（例：旋转）

1. `commands/` 里新建 `RotateCommand`（`.h/.cpp`），`id()` 用 `CommandIds.h`
   里新开的号；`redo()` 设**绝对终态**（`setShapeMeta(id, metaWithAngle)`），
   `undo()` 恢复快照；
2. 要不要合并？连续旋转 → 给 `mergeTag()`（`"rot:" + idsTag + ":" + gestureId`）
   和 `mergeWith()`（只覆盖 `to_`），并覆写 `mergeTagHasSession()`；
3. 目标安全：`scene->getMeta(id, &m)` 失败就 no-op（不崩、不误建）；
4. `estimatedMemory()` 自报载荷；
5. 入口：在 `CanvasView`（手势）或 `MainWindow`（按钮）里 `stack->push(...)`，
   **不要**先改 item 再补命令；
6. 测试：`unit_tests.cpp` 加一块（含"目标已删"和"合并只吸终态"两个断言），
   `SelfTest.cpp` 视情况加一步。

### 加一条契约测试

1. 在 `tests/unit_tests.cpp` 找最后一个 `// ── T20` 块，按同样格式续 `T21`；
2. 用 `TestCommand/SetVarCommand/UndoCounter` 当替身，**注入假时钟**别 sleep；
3. 断言"通知次数/游标/字节账/数值"四类里你真正承诺的那个；
4. 更新文件头的块数与 `README` 的断言数（它们是被 CI 当基线看的）。

## 7. 调试配方

| 症状 | 先看哪 |
|---|---|
| 撤销后数值不对 | `mergeWith` 是否累加了增量；`undoIn` 是否在命令基线快照失真的前提下用了（§8.2 字段自限） |
| 历史里出现"一条拖拽拆成好几条" | `gestureId_` 是否每次 press 递增、`mergeTag()` 是否带它 |
| 历史面板不刷新/闪 | 通知次数（T6）、`HistoryDock::refresh` 的增量分支 |
| 退出崩溃 | `~MainWindow` 拆除顺序；把 selftest 的 stdout 设成无缓冲再看最后一条 |
| 回放失败 | creator 的 `dynamic_cast` 是否成功、data 是否被双重转义 |
| 内存不降 | `estimatedMemory()` 是否自报真实载荷、合并路径是否过预算 |
